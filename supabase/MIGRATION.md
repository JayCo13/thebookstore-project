# FastAPI → Supabase migration

Full replacement of the `bookstore-backend/` FastAPI service with Supabase
(Postgres + Auth + Storage + Edge Functions). The frontend stays on Netlify; the
VPS/FastAPI backend is retired once this lands.

## Architectural decisions

1. **Integer PKs preserved.** Every table keeps its existing `int` id
   (`generated by default as identity`) so MySQL data imports verbatim and all
   FKs (`orders.user_id`, etc.) are unchanged. We did **not** re-key on
   `auth.users.id` (uuid).
2. **Auth bridge.** `public.users.auth_id uuid` links each app row to
   `auth.users`. A trigger (`handle_new_auth_user`) mirrors new Supabase signups
   into `public.users`, linking by email if a migrated row already exists. RLS
   helpers `public.app_user_id()` and `public.is_admin()` are the new equivalents
   of the FastAPI `get_current_user` / `require_admin` dependencies.
3. **Two access paths:**
   - **Direct (supabase-js):** plain reads/writes (catalog, profile, addresses,
     reviews, wishlist, reading own orders) go straight to Postgres through
     PostgREST, governed by RLS.
   - **Edge Functions (service_role):** anything with side effects or secrets —
     order creation, PayOS, GHN, order email, AI chatbot, admin login code,
     bulk import — runs server-side and bypasses RLS.
4. **CRA `api.js` keeps its surface.** The plan is to reimplement the named
   exports in `api.js` on top of supabase-js so page components barely change.

## What replaces what

### Direct supabase-js (no server code needed — RLS does the gating)

| Old FastAPI router | New |
|---|---|
| `books`, `stationery`, `authors`, `categories` (GET) | `supabase.from('books')...` etc. Redis caching → drop (PostgREST + CDN) or `Cache-Control`. |
| `books`/`stationery`/`authors`/`categories` (admin write) | `supabase.from(...).insert/update/delete` under `is_admin()` RLS |
| `slides` (GET + admin PUT) | `slide_contents` table |
| `notifications` | `notifications` table (RLS already filters `is_active`) |
| `addresses` | `addresses` table (owner-scoped RLS) |
| `reviews` / stationery reviews (read + own write) | `reviews` / `stationery_reviews` tables |
| `users` profile read/update, admin list/ban | `users` table RLS |
| `orders` (list own / read / admin list) | `orders` + `order_items` tables RLS |

> Verified-purchase check on review creation and "one review per book" upsert
> move into a Postgres `before insert` trigger or an RPC, since RLS alone can't
> express "must own an order_item for this book".

### Edge Functions (`supabase/functions/`)

| Function | Replaces | Notes |
|---|---|---|
| `create-order` | `POST /orders/` | guest+user orders, COD→insert+GHN+email inline, PayOS→park in `pending_orders` (no order row). ✅ done |
| `payos-create-link` | `POST /payments/payos/create-link` | calls PayOS, stores checkout url; takes `payos_order_code` (parked checkout) or `order_id` (legacy unpaid order) |
| `payos-webhook` | `POST /payments/payos/webhook` | HMAC verify → create the order from `pending_orders` (or mark an existing one Paid) → fulfill (GHN cod=0 + email). Must be deployed with `verify_jwt = false`. ✅ done |
| `ghn-sync-status` | `POST /orders/sync-ghn-status`, shipping-status GETs | GHN status polling |
| `chat` | `POST /chat/` | **hardest** — ChromaDB + sentence-transformers + Groq. See below. |
| `moderate-review` | `POST /moderation/review` | Groq call, stateless. ✅ done |
| `admin-login` | `POST /auth/admin/login` | validate rotating code, then sign in |
| `import-books` | `POST /books/import-xlsx` | parse XLSX (use a Deno xlsx lib) |
| `sitemap` | `GET /sitemap.xml` | or a Netlify function / prerender |
| `upload-media` | book/stationery image, read-sample, audio endpoints | put to Storage; optional resize |

Shared integration logic (`ghn_service`, `payos_service`, `email_service`,
`order_fulfillment`) → port to TS modules under `functions/_shared/`.

> **Zalo dropped.** Zalo OA / ZNS is fully removed — order notifications now go
> by **email** (`_shared/email.ts`, SMTP via the existing Gmail creds). No OAuth
> tokens to refresh/expire, so notifications are more stable. There is no
> `zalo_tokens` table, no `zalo-oauth`/`zalo-refresh` function, and no Zalo
> token-refresh cron.

### Auth specifics

- **Email/password + verification:** Supabase Auth built-in. `is_active` is kept
  in sync by the `on_auth_user_confirmed` trigger.
- **Password reset, welcome email:** Supabase Auth emails (customize templates in
  `config.toml` / dashboard). Retire `email_service` reset/verify paths.
- **Google OAuth:** Supabase native provider (configured in `config.toml`).
- **Admin login code:** keep the rotating 6-digit code as a gate, but issue it
  from a scheduled Edge Function (cron) instead of the asyncio scheduler.
- **JWT/bcrypt:** dropped — Supabase Auth owns tokens & password hashing. Legacy
  `password_hash` is import-only; existing users reset their password (or we run
  an admin migration to seed `auth.users`).

### Background tasks (old asyncio loops in `main.py`)

- `admin_code_rotation_scheduler` → Supabase scheduled function (pg_cron / cron
  trigger) hitting `admin-rotate-code`.
- `zalo_token_refresh_scheduler` → **removed** (Zalo retired; email needs no token refresh).

### The AI chatbot (the one real hurdle)

`sentence-transformers` (`dangvantuan/vietnamese-embedding`) + ChromaDB don't run
in Deno Edge Functions. Options:
1. **pgvector** in this same Postgres + generate embeddings via an API
   (e.g. a hosted embedding endpoint) — replaces ChromaDB cleanly, keeps Groq for
   chat. *Recommended.* Add a `book_embeddings` table with a `vector` column and a
   similarity-search RPC; port `embed_data.py` to write into it.
2. Keep a tiny Python embedding microservice (the one piece still on the VPS).
3. Drop semantic search; keyword-search the catalog for chatbot context.

## Deploying to the cloud (no Docker)

`db push` and `functions deploy` talk straight to the linked cloud project — no
Docker required (only `supabase start`/`db reset`/`functions serve` need it).

```bash
supabase link --project-ref <ref>     # one-time
supabase db push                       # applies migrations/ (incl. roles+slides seed) to the cloud DB
# deploy functions — see the JWT table below
```

Roles + default slides are applied by migration `20260601120400_seed_roles_slides.sql`
(not `seed.sql`, which is local-only). The admin user is created manually after
deploy (see "Admin user" above).

> Optional local stack (only if you install Docker): `supabase start` →
> `supabase db reset` (also runs `seed.sql`) → `supabase functions serve`.

## Deploying functions (JWT verification)

Public/server-to-server functions must be deployed with `--no-verify-jwt` (they
do their own auth or are called by external services); the rest keep default JWT
verification (the anon key is a valid JWT, so guests still pass).

```bash
supabase functions deploy payos-webhook    --no-verify-jwt   # PayOS server-to-server
supabase functions deploy admin-login      --no-verify-jwt   # public; validates code+pw itself
supabase functions deploy sitemap          --no-verify-jwt   # public XML
supabase functions deploy admin-rotate-code --no-verify-jwt  # cron; gates on service_role header
# default verification is fine for these (anon key passes; own-auth inside):
supabase functions deploy create-order
supabase functions deploy payos-create-link
supabase functions deploy ghn-sync-status
supabase functions deploy ghn-order-status
supabase functions deploy import-books
supabase functions deploy upload-media
supabase functions deploy moderate-review
supabase functions deploy chat
```

Point PayOS's webhook URL at `<project>/functions/v1/payos-webhook`, and set the
Netlify `/sitemap.xml` redirect/proxy to `<project>/functions/v1/sitemap`.

### Admin user

`seed.sql` can't create auth credentials. After `supabase start`, create the
admin in `auth.users` then elevate the mirrored row:

```sql
-- run via Studio SQL editor or psql against the local db
select auth.uid();  -- (after creating the user through the dashboard / signUp)
update public.users
   set role_id = (select role_id from public.roles where role_name = 'Admin'),
       is_active = 1
 where email = '<ADMIN_EMAIL>';
```

(Or script it with the Admin API + service_role key.)
